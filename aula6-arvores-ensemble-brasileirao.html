Bloco 1 — Engenharia de Atributos

Por que expandir as features?

Na Aula 5, o modelo linear tinha 3 features de saldo. Hoje, os algoritmos baseados em árvores capturam interações não lineares naturalmente — mas precisam de variáveis ricas para brilhar.

“Entra lixo, sai lixo”

Nenhum algoritmo — por mais sofisticado que seja — extrai signal de dados pobres. A Engenharia de Atributos é onde o cientista de dados mais agrega valor.

Vamos criar 3 grupos de novas features, todas calculadas só com o passado (sem data leakage):

  1. Forma recente: média móvel de gols nos últimos 5 jogos
  2. Aproveitamento mandante vs. visitante: rendimento específico
  3. Momento da tabela: diferença de pontos e saldo de gols

Ratings: o que já tínhamos (Aula 5)

Reutilizamos os ratings calculados somente com o treino (mesmo código da Aula 5):

stats_home <- treino |> group_by(time = home) |>
  summarise(jogos = n(),
            pontos = sum(3 * (gols_home > gols_away) + (gols_home == gols_away)),
            gm = sum(gols_home), gs = sum(gols_away))
stats_away <- treino |> group_by(time = away) |>
  summarise(jogos = n(),
            pontos = sum(3 * (gols_away > gols_home) + (gols_away == gols_home)),
            gm = sum(gols_away), gs = sum(gols_home))

ratings <- full_join(stats_home, stats_away, by = "time") |>
  mutate(across(-time, ~ replace_na(.x, 0))) |>
  transmute(time,
            aproveitamento = (pontos.x + pontos.y) / (3 * (jogos.x + jogos.y)),
            gm_medio = (gm.x + gm.y) / (jogos.x + jogos.y),
            gs_medio = (gs.x + gs.y) / (jogos.x + jogos.y))

Aproveitamento mandante vs. visitante

O aproveitamento geral mistura casa e fora. Mas jogar em casa é diferente de jogar fora! Criamos dois aproveitamentos separados:

ap_casa <- treino |>
  group_by(time = home) |>                               # ← só jogos como mandante
  summarise(ap_casa = sum(3 * (gols_home > gols_away) +
                          (gols_home == gols_away)) / (3 * n()))

ap_fora <- treino |>
  group_by(time = away) |>                               # ← só jogos como visitante
  summarise(ap_fora = sum(3 * (gols_away > gols_home) +
                          (gols_away == gols_home)) / (3 * n()))

Intuição: o Flamengo pode ter 70% de aproveitamento geral, mas 85% jogando em casa e só 55% jogando fora. A árvore pode explorar essa diferença.

Forma recente: média móvel de gols

A forma recente é dinâmica: muda a cada rodada. Para cada jogo, olhamos os 5 jogos anteriores de cada time (excluindo o jogo atual):

# Cada time aparece 2x por rodada (como mandante e como visitante)
team_games <- bind_rows(
  jogos |> transmute(date, time = home, opp = away,
                     gols_pro = gols_home, gols_contra = gols_away) |>
    mutate(pontos = case_when(gols_pro > gols_contra ~ 3,
                              gols_pro == gols_contra ~ 1, TRUE ~ 0)),
  jogos |> transmute(date, time = away, opp = home,
                     gols_pro = gols_away, gols_contra = gols_home) |>
    mutate(pontos = case_when(gols_pro > gols_contra ~ 3,
                              gols_pro == gols_contra ~ 1, TRUE ~ 0))
) |>
  arrange(time, date) |>                                 # ← ordena por time e data
  group_by(time) |>                                      # ← agrupa por time
  mutate(
    # Cumulativo ATÉ o jogo anterior (lag evita usar o jogo atual)
    pontos_cum     = lag(cumsum(pontos)) |> replace_na(0),
    saldo_gols_cum = lag(cumsum(gols_pro - gols_contra)) |> replace_na(0),
    # Forma recente: média dos últimos 5 jogos (exclui o atual)
    forma_gm = rowMeans(cbind(lag(gols_pro, 1), lag(gols_pro, 2),
                              lag(gols_pro, 3), lag(gols_pro, 4),
                              lag(gols_pro, 5)), na.rm = TRUE),
    forma_gs = rowMeans(cbind(lag(gols_contra, 1), lag(gols_contra, 2),
                              lag(gols_contra, 3), lag(gols_contra, 4),
                              lag(gols_contra, 5)), na.rm = TRUE)
  ) |>
  ungroup() |>
  mutate(across(c(forma_gm, forma_gs), ~ if_else(is.na(.x), 0, .x)))  # ← 1º jogo: sem histórico

Por que lag() evita data leakage

Sem olhar o futuro!

Cada jogo recebe sua forma calculada apenas com jogos anteriores. O lag() desloca a série temporal, garantindo que cada jogo só veja os jogos anteriores (do 1º até o 5º antes dele).

O cálculo é feito sobre todos os jogos realizados (não só o treino), mas cada ponto olha só para trás — não há vazamento.

Para os jogos do teste, a forma usa jogos do treino + jogos anteriores do próprio teste — exatamente como seria na vida real (prever a próxima rodada com tudo que já aconteceu).

Momento da tabela

As duas colunas pontos_cum e saldo_gols_cum capturam o momento do time na classificação até a rodada anterior:

  • pontos_cum → pontos acumulados (posição na tabela)
  • saldo_gols_cum → saldo de gols acumulado (desempate natural)

A diferença entre os dois times nesses indicadores vira feature:

  • dif_pontos → o mandante está quantos pontos à frente do visitante?
  • dif_saldo_gols → o mandante tem saldo de gols melhor quanto?

Juntando tudo: as 11 features

add_features_full <- function(df, ratings, ap_casa, ap_fora, team_games) {
  # Estatísticas globais por time (do treino)
  df <- df |>
    left_join(ratings, by = c("home" = "time")) |>
    rename_with(~ paste0(.x, "_home"), c(aproveitamento, gm_medio, gs_medio)) |>
    left_join(ratings, by = c("away" = "time")) |>
    rename_with(~ paste0(.x, "_away"), c(aproveitamento, gm_medio, gs_medio)) |>
    left_join(ap_casa, by = c("home" = "time")) |>
    left_join(ap_fora, by = c("away" = "time"))

  # Forma recente e momento da tabela (do histórico, só passado)
  home_stats <- team_games |>
    select(date, time, forma_gm_home = forma_gm, forma_gs_home = forma_gs,
           pontos_cum_home = pontos_cum, saldo_gols_cum_home = saldo_gols_cum)
  away_stats <- team_games |>
    select(date, time, forma_gm_away = forma_gm, forma_gs_away = forma_gs,
           pontos_cum_away = pontos_cum, saldo_gols_cum_away = saldo_gols_cum)

  df |>
    left_join(home_stats, by = c("date", "home" = "time")) |>
    left_join(away_stats, by = c("date", "away" = "time")) |>
    mutate(across(c(ap_casa, ap_fora), ~ replace_na(.x, 0.5))) |>  # ← fallback neutro
    mutate(
      saldo_forca    = aproveitamento_home - aproveitamento_away,  # ← Aula 5
      saldo_ataque   = gm_medio_home - gm_medio_away,              # ← Aula 5
      saldo_defesa   = gs_medio_away - gs_medio_home,              # ← Aula 5
      dif_pontos     = pontos_cum_home - pontos_cum_away,          # ← novo
      dif_saldo_gols = saldo_gols_cum_home - saldo_gols_cum_away   # ← novo
    )
}

Bloco 2 — Árvores de Decisão

A ideia: regras se/então

A Árvore de Decisão divide o espaço de dados em regiões ortogonais por meio de perguntas binárias simples:

“O saldo de força é maior que 0.3?” → Sim: “A forma recente do mandante é maior que 1.5?” → Não: “O aproveitamento em casa é maior que 50%?”

Cada nó faz uma pergunta; cada folha dá uma previsão (probabilidade de vitória do mandante).

Critérios de pureza: o quão “misturado” está o nó?

A árvore escolhe a pergunta que mais reduz a impureza do nó. Mas o que é impureza? É simples: quão misturado está o nó.

Nó puro (impureza = 0) ✅

10 vitórias, 0 derrotas → 100% de uma classe → a árvore para de dividir. Decisão tomada!

Nó misturado (impureza máxima) ⚠️

5 vitórias, 5 derrotas → 50/50 → máxima incerteza → a árvore tenta dividir de novo

A árvore testa todas as perguntas possíveis e escolhe a que mais deixa o nó puro. Dois critérios clássicos medem isso:

  • Gini (padrão do rpart) — mais simples, sem logaritmo
  • Entropia — mesma ideia, com logaritmo

Na prática, Gini e Entropia produzem árvores quase idênticas. O Gini é o padrão por ser computacionalmente mais barato.

Gini vs. Entropia: diferença prática

As duas curvas têm formato quase idêntico — na prática, Gini e Entropia produzem árvores muito parecidas. O Gini é o padrão do rpart por ser computacionalmente mais barato (sem logaritmo).

Prós e contras das árvores

Prós ✅

  • Interpretabilidade total (“modelo caixa branca”): qualquer árvore pode ser desenhada e lida por um leigo
  • Captura interações automaticamente (sem precisar criar termos de multiplicação à mão)
  • Lida com variáveis categóricas e numéricas sem pré-processamento
  • Não assume nenhuma forma funcional (linear, quadrática…)

Contras ❌

  • Sobreajuste (overfitting): cresce até decorar o treino
  • Instabilidade: uma mudança em poucos jogos gera uma árvore completamente diferente
  • Fronteiras ortogonais: só divide em “degraus”, nunca em diagonais suaves
  • Tende a enviesar para a classe majoritária se o dataset for desbalanceado

Regularização: poda da árvore

A árvore sem controle cresce até cada folha ter 1 só jogo → decora o treino. A solução é regularizar — exatamente como fizemos com o Lasso na Aula 5, mas com hiperparâmetros diferentes:

Hiperparâmetro O que controla Analogia com a Aula 5
cost_complexity Pedágio por folha extra — poda ramos que não valem a pena O “lambda” do Lasso
tree_depth Profundidade máxima — limita quantas perguntas em sequência Limite de coeficientes não nulos
min_n Mínimo de jogos por folha — evita generalizar de 2 casos Tamanho mínimo de amostra

Note

Conexão com a Aula 5: assim como o Lasso “cortava” coeficientes desnecessários, a poda corta ramos que não ajudam. Árvore grande demais = decora o treino (overfit); poda forte demais = simplão demais (underfit). O ponto ótimo está no meio.

Ajustando e tunando a árvore

tree_spec <- decision_tree(

  min_n = tune()                # ← mínimo de jogos por folha
) |>
  set_engine("rpart") |>        # ← implementação CART clássica

  add_model(tree_spec) |>

tree_grid <- grid_regular(      # ← 3 valores × 3 × 3 = 27 combinações
  cost_complexity(range = c(-4, -1)),   # ← 0.0001 a 0.1
  tree_depth(range = c(2, 8)),         # ← profundidade 2 a 8

O melhor ponto de poda

Leitura: árvores muito profundas (tree_depth = 8) com poda fraca (cost_complexity baixo) sobreajustam. O ponto ótimo fica no equilíbrio: profundidade moderada + poda que corta o excesso.

Como ler a árvore

Cada nó mostra:

  1. A regra de divisão (ex: dif_pontos >= 5.5)
  2. A previsão (sim/nao) e a probabilidade no nó
  3. A proporção de jogos no nó

  • Cada ramo cria uma região do espaço de dados

Curva ROC: acertos vs. alarmes falsos

A Curva ROC mostra como o modelo se sai em diferentes pontos de corte (thresholds):

  • Eixo X (FPR): quantos jogos o modelo “chutou vitória” e errou — alarme falso
  • Eixo Y (TPR): quantas vitórias reais o modelo acertou — sensibilidade
  • A linha tracejada é o “chute aleatório” (50/50). Quanto mais para o canto superior esquerdo, melhor o modelo

Use o controle deslizante abaixo para variar o threshold e ver como sensibilidade e alarme falso mudam juntos!

Primeiro, a matriz de confusão mostra quantos jogos o modelo acertou e errou no ponto de corte padrão (50%):

# Função reutilizável: plota ROC interativa com ponto animado
plot_roc_interativo <- function(pred_df, model_name) {
  roc_data <- roc_curve(pred_df, truth = home_win, .pred_sim) |>
    filter(!is.na(.threshold), is.finite(.threshold))

  # Limita os frames para uma animação mais fluida (~40 pontos)
  if (nrow(roc_data) > 40) {
    idx <- as.integer(round(seq(1, nrow(roc_data), length.out = 40)))
    roc_data <- roc_data[idx, ]
  }

  plot_ly(
    data = roc_data,
    x = ~1 - specificity,
    y = ~sensitivity,
    type = 'scatter',
    mode = 'lines',
    line = list(color = 'steelblue', width = 3),
    showlegend = FALSE
  ) |>
    add_trace(
      data = roc_data,
      x = ~1 - specificity,
      y = ~sensitivity,
      frame = ~.threshold,
      type = 'scatter',
      mode = 'markers',
      marker = list(size = 14, color = 'red',
                    line = list(color = 'white', width = 2)),
      text = ~paste0(
        "Threshold: ", round(.threshold, 3),
        "<br>TPR (Sensibilidade): ", round(sensitivity, 3),
        "<br>FPR (Alarme falso): ", round(1 - specificity, 3)
      ),
      hoverinfo = 'text',
      showlegend = FALSE
    ) |>
    layout(
      title = paste0("Curva ROC interativa — ", model_name),
      xaxis = list(title = "FPR (alarme falso)", range = c(0, 1)),
      yaxis = list(title = "TPR (sensibilidade)", range = c(0, 1)),
      showlegend = FALSE,
      shapes = list(
        list(type = 'line', x0 = 0, y0 = 0, x1 = 1, y1 = 1,
             line = list(dash = 'dash', color = 'gray', width = 1))
      )
    )
}

Bloco 3 — Random Forest

A sabedoria das multidões

Uma árvore é como um único torcedor opinando: pode acertar muito ou errar feio, dependendo do que viu. A Floresta Aleatória agrega a opinião de centenas de árvores independentes:

“Se você pedir para 500 pessoas diferentes palpitarem no Brasileirão, a média dos palpites será melhor que qualquer palpite individual.”

Isso é ensemble learning: combinar modelos fracos (árvores individuais) para produzir um modelo forte.

Referência: Géron, Cap. 7

A intuição é a mesma de pedir palpites a várias pessoas: se cada um vê informação diferente, a média dos palpites é melhor que qualquer palpite individual. Mais árvores = mais estabilidade. O segredo é garantir que elas sejam suficientemente diferentes entre si.

Bagging: amostragem com reposição

Como garantir que as 500 árvores sejam diferentes? Com aleatoriedade dupla:

  1. Bagging (Bootstrap Aggregating): cada árvore treina numa amostra com reposição do treino (~63% dos jogos únicos, 37% repetidos). Jogos que ficam de fora são os OOB (Out-of-Bag) — servem como validação embutida.

  2. Aleatoriedade nas features (mtry): a cada divisão, a árvore só considera algumas das 11 features para escolher a melhor pergunta. Se mtry = 11, todas as features competem. Se mtry = 3, só 3 sorteadas por nó.

O mtry baixo força diversidade: impede que todas as árvores escolham a mesma feature dominante (ex: saldo_forca) no topo.

Hiperparâmetros do Random Forest

Hiperparâmetro O que controla Valor típico
trees Número de árvores na floresta 500 (fixo)
mtry Features sorteadas por divisão tunar (2 a 8)
min_n Mínimo de jogos por folha tunar (5 a 20)

Tip

Por que fixar trees = 500? Mais árvores nunca prejudicam o desempenho (só estabilizam) — o custo é tempo de treino. 500 é o ponto onde o ganho marginal é desprezível. O que importa tunar é mtry e min_n.

Ajustando o Random Forest

Bloco 4 — Gradient Boosting (XGBoost)

Aprendizado sequencial

O Gradient Boosting muda a estratégia: em vez de árvores independentes (como no Random Forest), cada nova árvore é treinada para corrigir os erros residuais das anteriores.

Árvore 1: prevê P(vitória)        →  resíduo = real - P
Árvore 2: prevê o resíduo         →  P atualizada = P + passo × resíduo
Árvore 3: prevê o NOVO resíduo    →  P atualizada de novo
...e assim por diante
Conceito O que é
Resíduo O que o modelo atual ainda não consegue prever (real - previsto)
learn_rate Tamanho do passo: quanto do resíduo cada nova árvore adiciona
Árvores fracas Cada árvore é rasa (depth 3), sozinha é péssima — mas em conjunto, poderosas

Como difere do Random Forest

Random Forest 🌳🌳🌳

  • Árvores independentes (paralelo)
  • Cada uma vê uma amostra diferente
  • Agrega por votação/média
  • Reduz variância
  • Hiperparâmetro chave: mtry

Gradient Boosting 🌳→🌳→🌳

  • Árvores sequenciais (cada uma corrige a anterior)
  • Cada uma vê os resíduos
  • Agrega por soma ponderada
  • Reduz viés (aprende com os erros)
  • Hiperparâmetros chave: learn_rate, trees

Note

Menção a LightGBM e CatBoost: existem outras implementações de boosting (LightGBM usa binning de features para acelerar; CatBoost lida com categóricas nativamente). Em R, o xgboost é o motor mais maduro e integrado ao tidymodels.

Hiperparâmetros do XGBoost

Hiperparâmetro O que controla Valor típico
learn_rate Quanto do erro cada árvore corrige (passo do aprendizado) 0.001 a 0.1
trees Número de árvores sequenciais 50 a 300
tree_depth Profundidade de cada árvore fraca 3 (fixo)

Tip

Intuição do learn_rate: valor baixo = aprende devagar (precisa de mais árvores, mas comete menos overfit). Valor alto = aprende rápido, mas pode “passar do ponto”. O ideal é passo pequeno + muitas árvores.

# Função que avalia um modelo no teste
avaliar <- function(modelo, dados) {
  pred <- predict(modelo, new_data = dados, type = "prob") |>
    bind_cols(predict(modelo, new_data = dados, type = "class")) |>
    bind_cols(dados)
  bind_rows(
    roc_auc(pred, truth = home_win, .pred_sim),
    f_meas(pred, truth = home_win, estimate = .pred_class),
    kap(pred, truth = home_win, estimate = .pred_class),
    mn_log_loss(pred, truth = home_win, .pred_sim),
    accuracy(pred, truth = home_win, estimate = .pred_class)
  ) |>
    select(.metric, .estimate)
}

Resumo da aula

  1. Engenharia de atributos transforma conhecimento de domínio em features → o cientista agrega mais valor aqui que no algoritmo
  2. Árvore de Decisão = regras se/então, caixa branca, mas instável e propensa a overfitting → precisa de poda (cost_complexity)
  3. Random Forest = centenas de árvores independentes → reduz variância, estabiliza, e entrega feature importance
  4. Gradient Boosting (XGBoost) = árvores sequenciais que corrigem resíduos → reduz viés, geralmente o mais performático
  5. A comparação é justa só quando todos usam o mesmo split, as mesmas features e o mesmo teste
  6. Não existe modelo universalmente melhor — a escolha depende de interpretabilidade, performance, estabilidade e custo computacional
